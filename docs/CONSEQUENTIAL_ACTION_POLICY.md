# Connector-Neutral Consequential Action Policy

Google email/calendar is the first external-action adapter, but future connectors must not invent their own approval semantics.

This increment defines one server-owned consequential-action contract that every connector/action kind must register before it can cross the external mutation boundary.

## Registered action specification

Each action kind declares:

- stable action kind and version;
- required capability;
- allowed providers;
- approval TTL;
- post-approval execution TTL;
- reconciliation mode;
- destination fields;
- attachment policy;
- calendar/destination policy;
- guest-notification/reminder policy;
- whether execution requires a future timestamp.

Unregistered action kinds and unregistered provider/action combinations fail closed.

## Approval scope

Every prepared preview now contains an `approval_scope` generated by the backend.

It binds:

- contract/version;
- action kind/version;
- provider;
- capability;
- exact connection ID;
- connected account and immutable provider subject;
- SHA-256 of the exact payload;
- recipients/destinations;
- attachment/destination/reminder policy;
- reconciliation mode;
- approval expiry.

The existing `preview_hash` covers this scope as part of the immutable preview.

Approval validates the scope again. Execution validates it again immediately before claiming the provider mutation. A connection/provider/capability mismatch also fails closed.

Models, source documents, search results, and connector content cannot create or alter this authorization scope.

## Connector requirements

A future connector such as Outlook, document sharing, or social publishing must not be enabled by adding provider-specific execution code alone.

Before release it must:

1. add a typed input schema;
2. register the action kind in `action_registry.py`;
3. declare provider/capability/destination/reconciliation policy;
4. map the provider adapter only to registered kinds;
5. preserve prepare → immutable preview → explicit approval → committed execution claim → provider result/reconciliation;
6. add injection, identity, changed-payload, uncertain-outcome, idempotency, restart, and concurrent-claim tests;
7. pass real staging validation with explicitly authorized test accounts.

No generic URL, arbitrary HTTP, shell, or unrestricted browser action is part of this contract.

## Current registered actions

- `email_send` via Google Gmail send scope;
- `calendar_create` via Google owned-events scope.

The registry is an architectural safety boundary, not an indication that additional connectors are enabled.
